# Playbook: перевод книги с китайского на русский (опыт HTLB, 2026)

Полный опыт перевода «高性价比人生指南» (HowToLiveBetter): 31 глава + README + 4 длинные статьи + веб-интерфейс, ~1000 пунктов, ~370 строк источников. Документ — концентрат для запуска перевода на следующий язык (английский) и для любых подобных проектов «книга + источники + веб-версия».

Сопутствующие документы (не дублируются здесь):
- `TRANSLATION.md` — конвенции перевода (байт-верные зоны, маппинг полей, слаги файлов)
- `docs/localization-techniques.md` — каталог из 8 приёмов передачи реалий с примерами
- `QUALITY.md` — MQM-рубрика оценки качества и жёсткие правила (hard fail)

---

## 1. Принципы (что сработало)

1. **Всё, что является идентификатором, не переводится.** Источники (авторы, журналы, DOI, URL), номера НПА, машинные теги `<!-- 成本标签: ... -->`, все цифры — байт-в-байт. Переводится только метка поля (`- 来源：` → `- Источники:`). Это единственное, что делает перевод *проверяемым машино*.
2. **Конвенции до перевода.** TRANSLATION.md пишется первым: что байт-верно, маппинг меток полей, слаги файлов, статусная строка, тон. Каждый сабагент получает ссылку на неё, а не «переведи как в других главах».
3. **Форенизация + переводческий комментарий** (не доместикация): чужое остаётся чужим, читателя проводят помеченными вставками — глосса при первом упоминании, аналог телефона в скобках, блок «Примечание переводчика» в шапке главы. Ни одна вставка не выдаёт себя за оригинал.
4. **Проверяемость важнее уверенности.** Каждая глава после сборки проходит скрипт сверки: счётчики пунктов/тегов/источников, побайтовое совпадение источников, 0 иероглифов вне разрешённых зон. «Мне кажется, что всё ок» не принимается.
5. **1 глава = 1 коммит.** Отчёт заказчику каждые 5 глав. Мелкие атомарные коммиты = точечный откат и читаемый changelog для автора.

## 2. Пайплайн

```
книга (book/*.md, ~30КБ/глава)
   │  make_digest.py <NN>
   ▼
юниты 1–2КБ (units/NN.md) + blocks.json (теги+источники, LLM их НЕ видит)
   │  сабагенты: перевод юнитов, запись файла сразу
   ▼
units/*.md (переведённые, с заполнителями §TAG§/§SRC§)
   │  assemble.py <NN> <workdir> <out.md>
   ▼
сборка главы: инъекция источников байт-в-байт + сверка (items/tags/sources/hanzi)
   │  git commit (1 глава = 1 коммит)
   ▼
пост-волны: локализационный обзор → естественность → ретрофит названий → QA юнитами → reconciliation
```

### Почему юниты, а не главы
- Сабагент с целой главой (30–42КБ) либо таймится, либо «сгорает» в рассуждениях и не пишет файл.
- Юнит 1–2КБ = один пункт или два. Риск потери = один пункт, а не глава.
- Сборка и проверка централизованы: LLM физически не может испортить источники — они не входят в его контекст.

### Скрипты (в `tools/`)
| Скрипт | Что делает |
|---|---|
| `make_digest.py <NN>` | режет главу на юниты; теги и источники уходят в `blocks.json`, в юните — заполнители `§TAG§`/`§SRC§` |
| `assemble.py <NN> <workdir> <out.md>` | собирает главу, инъектирует блоки байт-в-байт, проверяет счётчики и источники, WARN по непереведённым строкам; exit ≠ 0 при FAIL |
| `watchdog.py <run-dir>` | монитор: недостающие юниты + стагнация (нет записей 25+ мин); для cron-периода |

## 3. Сабагенты: как использовать

### Волны параллельно
- Перевод: 5–6 сабагентов параллельно, по 1 юниту на каждого. Крупные главы (13 — 42 пункта) режутся на 2 волны.
- Ревью: волны по главам/аспектам. QA — юнитами по ~10 пар строк, 8 параллельно; 316 строк проверены за ~12 минут (целые главы — 50+ минут и таймауты).

### Контракт с сабагентом (проверено)
1. **«Работа = запись файла»** — без анализа, без планирования, без изучения других глав.
2. Стиль-сэмпл даётся в задаче (2–3 предложения из готовой главы), а не «посмотри в главе 17».
3. Результат = файл. Никаких JSON-отчётов про перевод.
4. QA-агенты — read-only: пишут только вердикт-JSON `{unit, checked, issues:[...]}`. **Никогда не давать QA-агентам править book/ в общем worktree.**
5. Перед агрегацией: число вердиктов == число юнитов. Агрегация фиксов — в Python централизованно, а не вручную.

### Восстановление после падений
- Транскрипты сабагентов лежат в `~/.hermes/cache/delegation/` — работа не теряется, переотправляется «сборочный» агент, а не перевод с нуля.
- Провайдер делегации: дешёвые шлюзы таймятся на длинной генерации (120–600с). Прямой провайдер (z.ai) + юниты малого размера = 0 таймаутов.

### Фоновые пайплайны-конкуренты
- Старый systemd-юнит (`htlb-pipeline.service`) с устаревшим промптом перезаписывал свежие главы. Перед волной: проверить параллельные `hermes -z` процессы и state-файлы пайплайнов; нейтрализовать (записать в state все главы = сам остановится).

## 4. Верификация (скриптовая, не на глаз)

Обязательные проверки после сборки каждой главы:
1. Счётчик пунктов (`### N.`) — равен оригиналу.
2. Счётчик тегов `<!-- 成本标签` — равен оригиналу.
3. Источники: построчно байт-в-байт после нормализации метки (`- 来源：` vs `- Источники:`; у RU-метки допускается хвостовой пробел — нормализуй `^- Источники:\s?`).
4. 0 иероглифов вне разрешённых зон (источники, теги, ссылки на оригинал, шапка).
5. Вставки вырезаются перед сверкой: `(…中文…)`, `[рус. «…»]`, `> Примечание переводчика:`.

**Грабли верификатора** (давали ложные расхождения):
- `[рус. «…»]` с ВЛОЖЕННЫМИ «…» внутри: вырезать от `' [рус. '` до ближайшего `]`, не регэкспом `[^»]*»` (гл. 17).
- Запятая/точка в десятичных (0,58 vs 0.58) — нормализовать; 0.58 vs 0.580 — НЕ нормализовать.
- 万 — это конверсия (1万 = 10000), не «перевод»: 2 万 = «20 тысяч юаней».
- Считать grep-ом по стволу слова (инфлективные формы прячут остатки), не по точной форме.
- Доверять grep, а не заявленному в задании числу источников — заявленные счётчики ошибались.

## 5. Качество текста (волны после перевода)

Порядок волн (каждая — параллельные сабагенты + централизованное применение фиксов + рескрипт верификации):

1. **Локализационный обзор**: глоссы реалий при первом упоминании, аналоги набираемых телефонов, блоки примечаний для страновых фактов. Итог: 48 глосс, 34 аналога, 8 примечаний.
2. **Естественность**: поиск калек и канцелярита (когорта, экспозиция, конфаундинг → живой русский). 67 находок → 73 фикса в 24 главах. Ищи grep по стволу термина.
3. **Ретрофит названий источников**: `[рус. «…»]` после китайского названия, 371 строка, 6 сабагентов. Потом QA юнитами (10 проблем найдено и исправлено).
4. **Two-translator reconciliation**: те же пункты переводятся вторым «переводчиком», расхождения = кандидаты в смысловые ошибки. 11 фиксов.
5. **Native-editor pass**: финальная шлифовка носителем. 149 правок.

Правки применяются патчем по точной строке; после каждой волны — повторная скриптовая сверка (правки ломают структуру чаще, чем кажется).

**Жёсткие правила QUALITY.md** (авто-фейл независимо от балла): изменённая цифра/DOI/URL; неверный HR/RR/OR/CI; тег не байт-в-байт; источники не байт-в-байт; выдуманный LLM-факт; нет статусной строки/ссылки; счётчик пунктов ≠ оригиналу.

## 6. Веб-версия (GitHub Pages)

- `index.html` — однофайловый веб-интерфейс, читает `README.md` как данные. Для русского: двуязычный (по умолчанию RU, кнопка «中», `?lang=zh`), парсеры полей понимают обе метки (`(?:成本|Стоимость)` и т.д.).
- **Ключи данных не переводятся**: `data-v="少"`, значения тегов, ключи LABEL — только видимый текст.
- Локализация UI: все видимые строки, включая бейджи карточек (значения данных вроде 极高 отображаются через словарь RATIO_LABEL), панель ?perf=1, состояния загрузки/ошибок.
- **Аудит остаточной китайщины** (regex по `\u4e00-\u9fff` и полноразмерной пунктуации `，。：；`): исключения — data-v ключи, имя оригинала в шапке, переключатель языка, комментарии в `<script>`.
- Русский текст длиннее китайского: ломает flex-строки «заголовок ←→ подсказка» (→ column), требует wider intro (72ch → 100%), ломает узкие сетки.
- Деплой: push в main → Pages пересобирается; проверка живого сайта через 50+ сек: `curl -s <url> | grep -o 'фрагмент'`.

## 7. Работа с автором (upstream)

1. **Первый контакт — issue на языке автора** с предложением перевода, до начала работы.
2. Лицензия: проверять LICENSE до всего (Unlicense = можно всё).
3. PR: двуязычный заголовок, ссылка на issue, 1 глава = 1 коммит — автору удобно ревьюить и по частям принимать.
4. Отчёты автору — на его языке, коротко, со ссылками.
5. Правки от автора (нейтральность телефонов, «не выдумывать термины») применяются сразу и отражаются в TRANSLATION.md, чтобы не повторились.
6. Слияние в main форка только по завершении всего корпуса; затем GitHub Pages; затем финальный комментарий в issue со всеми ссылками.

## 8. Чек-лист запуска нового языка (EN)

1. [ ] LICENSE, issues, CONTRIBUTING — проверены.
2. [ ] Issue автору на китайском (или языке автора) — предложение EN-версии.
3. [ ] TRANSLATION.md: секция EN (метки полей: 成本→Cost, 说人话→In plain terms, 收益→Benefit, 证据等级→Evidence grade, 来源→Sources, 备注→Notes), слаги файлов (решить: английские или зеркало китайских; не смешивать схемы).
4. [ ] Статусная строка и бэк-линки с пересчитанной глубиной (`book/en/x.md` → `../../README.md`).
5. [ ] `make_digest.py` уже готов — юниты те же; блоки инъектируются как есть.
6. [ ] Волны по 5–6 сабагентов; контракт «работа = запись файла»; стиль-сэмпл в задаче.
7. [ ] `assemble.py` проверяет каждый файл; правило «источники после метки байт-в-байт» в силе.
8. [ ] Волновики: локализация → естественность → ретрофит `[eng. "…"]` → reconciliation → native pass.
9. [ ] README.en.md + язык-селектор в README.md (строка уже есть — добавить EN рядом с RU).
10. [ ] Веб: добавить EN-режим в index.html (парсеры уже толерантны — расширить маппинг полей и словари LABEL/RATIO_LABEL).
11. [ ] Финал: merge в main, Pages, комментарий автору в issue.

## 9. Топ-10 граблей (сводка)

1. Сабагент сжимает рассуждениями весь лимит и не пишет файл → контракт «пиши сразу».
2. Провайдер делегации таймит длинную генерацию → юниты 1–2КБ + прямой провайдер.
3. Заявленные счётчики источников врут → считать grep-ом.
4. Вложенные «…» в `[рус. «…»]` ломают наивный регэксп вырезания вставок.
5. RU-метка `- Источники:` с хвостовым пробелом vs ZH без — нормализовать перед сравнением.
6. Старый фоновый пайплайн перезаписывает свежие главы → проверять конкурентов перед волной.
7. Русский текст длиннее китайского → UI-плейки (flex, 72ch, узкие сетки) ломаются.
8. data-v/ключи данных случайно переводятся → фильтры молча ломаются.
9. Правки ревьюеров ломают структуру → скриптовая сверка после каждой волны.
10. Удаление форка до мержа PR автозакрывает PR → форк не трогать до слияния.
