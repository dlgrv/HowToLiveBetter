# Протокол валидации новых пассов пайплайна (CN→RU/EN)

Назначение: доказать, что пассы A–E улучшают перевод, а не добавляют шум. Соло-воркфлоу, минимум времени Лёни (одна Telegram-сессия ~15–20 мин), всё воспроизводимо скриптами в `tools/validate/` с фиксированными seed и JSON-артефактами.

Пассы:
- **A** — стиль-маркеры регексами в verify.py (канцелярит, причастные цепочки, страдательные) → WARN.
- **B** — QE-скор CometKiwi на главу + правило регресса.
- **C** — MHP source-blind судья беглости (сабагент, A/B).
- **D** — локальный LLM-судья на Mac (Qwen3), source-blind A/B по юнитам.
- **E** — semantic fact-check пасс.

Общие принципы: judge'и валидируются против золотого набора и против Лёни (Cohen's kappa), регексы — против FP-аудита, fact-check — против инъекционных мутаций. Ничто из нового не блокирует коммит, пока не валидировано; A всегда только WARN.

---

## Шаг 0. Инфраструктура (однократно, ~1 ч агента, 0 токенов API)

Скрипты в `tools/validate/`:
- `qe_noise.py` — шум/порог CometKiwi (шаг 1).
- `golden_pairs.py` — сборка золотых A/B-пар со стратификацией и фиксированным seed, маппинг пар→вердикты в JSON (шаг 2).
- `judge_agreement.py` — kappa/совпадения судья↔Лёня, judge↔judge, bias-метрики (шаг 3).
- `style_fp_audit.py` — прогон A по всем главо-языкам, выборка WARN-ов на аудит (шаг 4).
- `mutation_test.py` — инъекция 30 семантических мутаций + контрольных чистых юнитов для E (шаг 5).
- `nativeness_rate.py` — книг-левел метрика (шаг 7).

Артефакты: `tools/validate/results/*.json` (seed, ID пар, вердикты) — коммитятся, чтобы любой прогон повторялся.

## Шаг 1. Калибровка QE-регресс-правила (B) — без пользователя

1. Зафиксировать конфиг CometKiwi (модель, вес/квантование, бэкенд, версия скрипта) в `tools/validate/results/qe_config.json`. Смена конфига = пересборка baseline.
2. Якорные главы: 01, 13, 24 (маленькая/большая/средняя) × ru + 13×en = 4 текста. По 5 повторных прогонов: 3 с тем же конфигом (порядок сегментов перемешан) + 2 на вариации прецизионности/батча, если доступны.
3. Считаем per-chapter stdev σ на НЕизменённом тексте. Порог терпимости τ = max(3σ, 0.01 abs на шкале 0–1).
4. Якорь «полезного» дельта: прогнать pre-fix версию ru13 (история: кальки «когорт» ×13, найдены verify.py) vs текущую. Реальное улучшение должно быть ≥ 2τ, иначе правило нечувствительно и его надо пересобрать (per-unit вместо per-chapter).
5. Правило регресса: глава помечается при падении > τ против baseline И подтверждении вторым прогоном. Метрики: per-chapter score + mean нижнего квартиля юнитов (ловит локальные повреждения, усреднённые на уровне главы).
6. Итого замеров: ~20 скорингов, ~1 ч Mac-времени, 0 токенов.

## Шаг 2. Золотой набор A/B-пар (одна Telegram-сессия Лёни, 15 мин)

1. Стратификация: 6 глав по жанрам — 01 (медицина), 10 (деньги), 13 (экстренное), 16 (хроническое), 24 (врач), 30 (ребёнок) × ru/en.
2. Три страты качества: (a) чистые после MQM, (b) verify-WARN/калько-тяжёлые, (c) свежие случайные. Пары: A = текущая версия, B = деградированная контролируемым трансформом (обезличенный калька-вставка, буквализация фразы, канцелярит, пассивная цепочка; числа НЕ трогаем — их ловит verify.py).
3. Объём: **60 пар Лёне** (18 с/пару ≈ 15 мин) + 10 пар-приманок A=B (одинаковые) как контроль внимания. Судьи C и D размечают те же 60 + ещё 60 расширенных (120 всего) для стабильности оценки.
4. Оформление Telegram (субагент присылает по одной паре): «Вариант 1 / Вариант 2» (порядок рандомизирован по seed, источник не показывается), ответ — одно число `1`, `2` или `=`. Батчами по 10 пар. Маппинг «вариант→оригинал» хранится только в JSON.
5. Судейский промпт: «Какой вариант читается как написанный носителем? Ответь строго 1/2/=» — без объяснений (иначеjudge рационализирует).

## Шаг 3. Согласованность судей (C и D одновременно)

1. Метрики: процент совпадений и Cohen's kappa с вердиктами Лёни на 60 парах.
2. Bias-контроль: на приманках A=B судья обязан отвечать «=» — ложных предпочтений ≤ 10%; на деградациях судья предпочитает чистый A ≥ 75%.
3. Межсудейская корреляция C↔D на тех же парах: расхождение > 40% = один из судей сломан (ищем, кто расходится с Лёней).
4. Пороги: **κ ≥ 0.6 — судье можно доверять** (использовать как решающий сигнал A/B); **κ 0.4–0.6 — только советник** (флаги для MQM-приоритизации, не решения); **κ < 0.4 — выбраковать**.

## Шаг 4. Валидация стиль-регексов (A)

1. Прогнать по всем ~62 главо-языкам (`style_fp_audit.py`), собрать все WARN.
2. Выборка на аудит: ≥ 100 фрагментов, минимум 25 на каждый класс правила. Сабагент пре-фильтрует очевидные FP, Лёне в ту же Telegram-сессию уходят только спорные (~20 шт., +5 мин).
3. Recall-якорь: 20 известных плохих фрагментов из истории фиксов (кальки, канцелярит из волн фиксов) — правило класса должно ловить ≥ 60% своих.
4. Статус всегда WARN-only: регексы не блокируют коммит, только приоритизируют MQM-волну.

## Шаг 5. Валидация semantic fact-check (E) — мутационное тестирование, без пользователя

1. `mutation_test.py` инъецирует 30 семантических мутаций в чистые юниты (перепутать направление риска, подменить вмешательство/субъекта, внести противоречие между юнитами одной главы) + 30 нетронутых контролей.
2. Пасс E прогоняется вслепую; считаем catch-rate и FP на контролях.
3. Пересечение с verify.py: доля находок E, дублирующих числовой гейт, должна быть ≤ 30%, иначе E избыточен.

## Шаг 6. Порядок внедрения и стоп-точки

1. Неделя 0, параллельно, 0 мин Лёни: шаг 1 (B-шум, Mac) ∥ шаг 4 прогон A + сабагент-преаудит ∥ сборка шага 5.
2. Единственная Telegram-сессия (~20 мин): 60 золотых пар (15 мин) + спорные FP регексов (5 мин).
3. Шаг 3: κ для C и D, межсудейская сверка.
4. **Стоп-точка 1**: если κ < 0.4 у ОБОИХ судей — проблема в дизайне пар или промпте, а не в пассах: переделать пары, максимум ОДНА повторная сессия; иначе пассы C/D закрыть.
5. Внедрение в волну (только принятые пассы): verify.py (гейт) → A WARN'ы (приоритезация MQM) → B дельта vs baseline с 2-прогонным подтверждением → D/C A/B только на WARN'ах и нижнем квартиле юнитов (бюджет-кап ~20 юнитов/главу).
6. **Стоп-точка 2**: после первой полной волны с принятыми пассами сверить nativeness rate и QE-тренд; если обе метрики в пределах шума — переосмыслить пассы, а не подкручивать пороги.

## Шаг 7. Итоговый эффект на уровне книги

1. **Nativeness rate**: судья (валидированный C или D, source-blind) на стратифицированной выборке 10 юнитов/главу (фиксированный seed, обновляется раз в волну) отвечает «пахнет ли переводом»: метрика = % юнитов «как у носителя». Baseline фиксируется до внедрения.
2. Тренд по главам после каждой волны: цель ru ≥ 75% и рост ≥ +5 п.п./волну при QE-дельте ≥ −τ; стагнация обоих = сигнал шага 6.7.
3. Пользовательский контроль: 5 случайных юнитов/месяц (~3 мин) — сверка вердиктов судьи с Лёней, дрейф κ < 0.5 = пересудья.
4. Дашборд: `nativeness_rate.py` пишет JSON+маркдаун-тренд по главам в `tools/validate/results/`.
